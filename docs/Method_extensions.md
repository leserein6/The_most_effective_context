# 工作方法插件 · 设计与实施方案

## 目标与接入边界

现有 Harness 先锚定 Project，按五类 Task 选择二级路由，通过 Evidence 执行，再由主 Agent 统一写回。测试工程已有多处路由引用。新增横跨设计、学习和调研的能力时，希望作者只维护自己的插件，用户可以按工作区启停。

本次扩展点设在选定 Task 之后、展开具体方法之前。主 Agent 是使用者，声明文件定义接口，插件目录提供实现。借鉴 DeepSeek Harness 对接口、提供者与使用者的区分，沿用本项目的 Python 和 Markdown 执行环境。Project 数据格式、原生 Skill 与已有的核心方法继续走各自的入口。

## 契约

每个内置插件位于 `extensions/<id>/`，通过 `extension.json` 声明。目录名使用小写字母、数字和连字符，以字母开头。v1 支持 Markdown 工作方法和显式列出的 Markdown 资源。查看[全景图声明](../extensions/panorama/extension.json)作为最小实例。

| 字段 | 谁使用、怎样使用 |
|---|---|
| schema_version、id | 构建和发现时检查兼容性与目录身份，v1 的版本号为整数 1。 |
| tasks、when、output | 主 Agent 从当前 Task 的候选摘要中按适用条件选择，输出说明用于验收。 |
| entry | 命中后读取的方法正文，相对插件目录定位。 |
| resources | 插件作者明确列出的配套文件，按方法正文指引读取。构建只收录声明、入口和这些资源。 |

新包随独立运行包交付。两种安装布局均把插件放在 Harness 根下。已安装的 v1 主机也可以直接放入完整的新方法包，下一次发现即生效。已安装插件默认启用，工作区通过插件 ID 保存停用标记。停用立即从下一次候选查询中生效，Project 历史产物继续归 Project 所有。发现只输出摘要，语义匹配由主 Agent 执行。声明故障应报告，核心任务仍可使用原路由。

## 执行顺序与验收

1. 实现声明发现、筛选和启停，将同一声明用于打包与安装。在空目录及嵌入业务仓库的布局验收。
2. 在主入口接上一次通用候选查询。添加临时第二个插件，确认无需编辑路由、构建脚本或核心白名单。验证未声明文件不会随包交付。
3. 交付有来源的滚雪球建图方法和用户提供的微服务图。在同一插件声明内加入第二张图，验证能随包安装。
4. 实测题对：“从零设计 Go DAO”应展开对象，“修复已定位的 SQL 拼写”直接处理。当前版本的 CLI 可以验证候选筛选、停用和资料可达性；最终的自然语言选择需要在 CodeBuddy 对话中观察。

首次升级旧 Workspace 时，在空目录安装新版用于比对；合入主入口的通用查询段，复制 scripts/extensions.py 和所需插件目录。已有定制的同名文件先对比差异。保留原 Project、日志及宿主入口指向。独立停用全景图即可回退其路由行为。
