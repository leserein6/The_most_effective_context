# Verify：每项声明都对应实际证据

任何模式即将声称已完成、已修复、已写入或测试通过时使用。输入是拟作出的声明、验收条件、当前产物和检查记录。

## 步骤

1. 拆开声明：“代码已改”“测试通过”“需求满足”“已提交远端”“实际 CLI 可用”是五个不同命题。
2. 为每项指定直接检查：修改看目标差异/内容，程序看实际运行结果，远端看目标分支和文件，行为看验收场景。
3. 检查已有记录是否针对当前产物版本且覆盖该命题。修改后旧结果失效；未再变化且证据充分时不反复重跑。
4. 缺证据时运行适合该命题的检查。读完整相关结果和退出状态，不只看“命令成功启动”。截断关键输出需继续读取。
5. 写验收对应表：条件｜证据位置/版本｜PASS/FAIL/UNVERIFIED｜限制。
6. 只声明已经证明的部分。保存失败、工具不可用、原故障未复现都要如实保留；本轮检查通过不自动改变 Project 状态。

## 常见错配

| 现有证据 | 不能推出 |
|---|---|
| 单元测试通过 | 跨服务流程或目标模型运行已通过 |
| 文件已创建 | 需求正确或系统可运行 |
| Subagent 声称成功 | 实际产物已经被核实 |
| Python 管理测试通过 | CodeBuddy 一定加载协议、DeepSeek 一定执行正确 |
| 某个样例正确 | 所有边界、并发和故障路径正确 |

最终回复简述成果、有效检查和剩余限制；详细命令留日志。无条件可检查时标 UNVERIFIED，给出可执行的验证办法，不换词包装成功。
