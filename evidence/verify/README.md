# Evidence: Verify（完成声明校验）

**Use when**：即将向用户声称“已完成、已修复、测试通过、提交成功、项目已创建”等可核实结果。  
**Don't use when**：只是讨论方案，没有任何完成声明。对简单回复仍应避免夸大。

## 完成声明前的 Gate

1. **列出要声称什么**：例如“文件写入远端”与“程序能运行”是不同命题，需要不同检查。
2. **为每个命题找直接验证**：文件→重新读取；代码→执行适当测试；提交→核实远端 SHA/路径；项目创建→读取正式项目实例并与确认草案比较。
3. **执行并读取结果**：尽可能使用当前工作环境的最新检查；不仅看工具调用成功，也要检查输出、错误与适用范围。
4. **只说已证实的部分**：没有测试不得说测试通过；检查了 README 不等于应用功能已验收。
5. **无法验证时明确降级**：写“已提交文件，但未验证程序运行”，而不是包装成完整交付。

## 对比示例

| 想要声称 | 至少需要 | 不足以支持 |
| --- | --- | --- |
| 测试通过 | 本次相关测试的可核对运行结果 | 曾经通过、代码看着没问题 |
| 文件已写入 | 目标位置真实存在并能读取 | 只在回复中贴了文件内容 |
| Bug 修复 | 原始症状回归验证成功 | 修改了可能相关的代码 |
| 需求已满足 | 对照实际验收项核查 | 单个测试通过 |

**参考方法**：Superpowers `verification-before-completion` 的“先查证，再声明”及按具体主张选择具体检查；本项目将它改成通用文件/项目操作，不只覆盖编码。
