# Execute：交付实际改动与验证

适用：用户要求修改代码、文件、配置或外部系统。仅要解释/审查不进入实施。输入：目标与验收、已确认约束、现有代码/资料、允许写入范围。

## 执行步骤

1. 查工作目录和现有差异，识别用户已有修改；读取相关源码与仓库真实构建/测试入口，不覆盖未知改动。
2. 对照计划或需求，写清本次改动范围；缺少关键决定转 clarify。普通实现选择沿用现有代码风格，自行处理。
3. 每次完成一个能检查的行为。代码变更理解输入→状态变化→输出/错误，再修改；不只改最终输出让样例过关。
4. 新增/修复行为按需增加有意义的验证；若计划约定 TDD 则执行红绿检查。文档/低风险改动不用机械增加实现镜像测试。
5. 执行仓库中实际可用的检查，保存命令、退出结果、关键输出和对应改动版本。失败先定位，不改测试期待来掩盖问题。
6. 自查差异：漏做/多做、错误返回、边界、并发、数据写入及兼容性；只有相关风险才按清单深查。
7. 交给 verify 校验本轮声明。主 Agent 按维护协议保存项目状态和操作流水；子 Agent 只回传报告。

## 分支

测试失败 → debug，保留失败事实。
工具缺失 → 写明哪些验证做不了和替代检查，不伪造 PASS。
旧决策冲突 → 先指出，明确修订才能更改。
外部副作用结果不明 → 查询是否生效，不盲目重试。
单纯无关检查失败 → 说明范围与证据，不顺手扩改整个仓库。

## 输出

实际改变/产物位置；已执行检查及结果；未验证或未完成项；必要下一步。
编排中实现者用 [实现 Prompt](../prompts/implementer.md)；不自行派生审查 Agent，不自动 commit/push。
