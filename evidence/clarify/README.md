# Clarify：把模糊要求变成明确决定

你负责消除会影响交付的歧义。不要通过堆问题显得周全，不要替用户虚构目标，也不要在用户只讨论时开始实现。

## 何时进入 / 需要什么

用户要求追问、目标有关键缺口、或新要求与已确认决策冲突时进入。先读本轮要求、项目定义和相关决定；代码事实按需查，不先扫描全部仓库。任务已经明确时直接交给下一方法。

## 执行步骤

1. 列出已经明确的目标、约束、验收条件，并为每项注明来源。已有答案不再问。
2. 把未知项分为：可查事实（你去查）、影响结果的用户决定（要问）、不影响交付的实现细节（你自行选）。
3. 给待定决定标依赖：例如先明确“是否离线”，再决定“云端数据同步”。不要把尚不成立的下游问题塞进当前问卷。
4. 把当前前提已明确的问题集中成一轮；每题说明会影响什么，给出推荐及理由，允许用户自由修改。用户要求一次问完时，不逐题打断。
5. 回答按题号应用。“都按推荐”只确认已展示的推荐；单独一句“是”无法判断对应多题时，针对歧义问清，不批量扩张授权。
6. 更新剩余问题；只对新产生且影响结果的分支追问。关键问题清楚即停止，不追求穷尽所有细节。

## 判断分支

| 情况 | 下一动作 |
|---|---|
| README 已写明数据库/语言 | 读取并采用，不问“用什么技术栈” |
| 用户还未确定产品目标 | 问期望结果，不先给数据库选型 |
| 旧决定与新要求冲突 | 展示具体冲突；明确修订则采用，否则询问 |
| 只有局部非关键未知 | 标为你的实现选择，继续 |
| 需创建 Project | 交给 Project Create 的名称/类型/一句话目标确认，不自行创建 |

## 输出格式

已明确：目标、范围、约束（只列与本轮有关的内容）。
待决定：Q编号｜问题｜决定后影响｜推荐及理由。
已收敛时：本轮结果要求、验收条件、仍待定但不阻塞的项、下一步。

反例：“加导出功能”且项目已有 CSV 规范，不再问格式；但若输出包含未确定是否允许导出的个人字段，应问字段边界，而非擅自全导出。

完成条件：没有阻塞正确执行的未决决定，用户要求的确认已取得；不是“已经问过一轮”。
