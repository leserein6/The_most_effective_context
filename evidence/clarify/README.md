# Evidence: Clarify / Grill-me（需求澄清）

**Use when**：用户明确希望被追问，或者关键不确定性会实质性改变交付、权限、范围或验收。  
**Don't use when**：上下文已经回答问题、缺失的只是可推迟的小细节。

## 工作流

1. **先检查已有上下文**：阅读用户给出的需求、决策和必要资料；绝不让用户重复已经说清的信息。
2. **找决策分叉**：确定“不问清楚会导致哪两个明显不同的结果”；优先识别动机、预期效果、硬约束和验收标准。
3. **每轮问一个高信息增益的问题**：说明已知部分并提出一个具体问题；不得同时抛出长问卷，亦不得用预设选项限制用户自由回答。
4. **渐进式收敛**：随着答案到来，修正理解；清楚到能形成可信草案或执行下一步时，主动停止追问。
5. **明确确认边界**：需求已澄清不等于获得持久化或高风险操作授权。需要创建 Project 时，返回 [Project Create](../../project-management/protocols/create.md) 展示草案并取得确认。

## Few-shot

用户：「做一个 AI 生活软件。」→ 核心用途不明，先问「你最想让它解决的一件具体麻烦是什么？」；不能直接确定技术栈、十个模块。  
用户：「本地 CSV 上传页，展示各列缺失率，不用登录。」→ 基本交付已明确，直接形成草案或执行，不应强制问商业模式。
