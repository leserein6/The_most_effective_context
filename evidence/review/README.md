# Review：独立核查需求与实现

默认只读。需要需求/规格、约束、审查范围、当前差异或产物、实现者声明和验证记录。缺哪些就标哪些，不能假定“代码看着合理=需求已满足”。

## 步骤

1. **固定对象**：确定 base/head、工作区差异或确切文档版本。范围不明先读上下文能确认的基线，仍多义才询问；不审一个移动中的目标。
2. **需求轴**：逐项检查是否实现、是否多做、是否误解；每项对应产物定位。无规格只能给实现质量结论，不补造需求后宣布符合。
3. **质量轴**：检查数据流、错误处理、边界、并发、资源生命周期与兼容性中相关项。代码外依赖只有为验证具体风险才追查。
4. 实现者报告当作待核声明。证据必须绑定同一版本；已有有效检查不机械重跑，有具体疑点时执行针对性检查。
5. 每个问题写出“输入/并发/故障条件 → 实际路径 → 后果 → 文件位置/依据”。无法构造依据的疑虑列待验证，不充当确定缺陷。
6. 合并重复问题，按真实影响分级：错误余额/重复扣款/数据损坏等为高风险；正确性或契约失配阻塞；一般可维护性建议不夸大成灾难。

## 输出

需求符合：PASS / FAIL / UNVERIFIED + 未核实项。
实现质量：PASS / FAIL / UNVERIFIED。
问题表：级别｜触发场景｜位置｜后果｜证据｜建议。
验证范围与盲区。无问题时明确未发现，不为凑数列格式偏好。

报告中的 PASS 仅覆盖写明范围；需要修改时交执行者，审查者不动工作区、不替用户审批合并。

用 [审查 Prompt](../prompts/review.md) 派发；交易/并发代码按需读风险清单。
