# Plan：把方案拆成有依赖、可验收的工作

**核心问题：怎样把已明确的目标分成可执行工作项，保证顺序正确、接口接得上、验收不遗漏？**

输入是目标/规格、约束、相关实现位置与预期验收。缺关键设计先解决，不在计划里藏一个“实现时再决定”的重大分歧。简单修改只列必要步骤。

## 1. 从验收结果反推工作

把每项可观察验收条件对应到实际产物，再反推产生该产物需要的改动。

例如“重启后仍能读取待办”需要持久化写入、启动读取及重启场景验证；只列“实现存储层”无法确认这项要求是否覆盖。

检查双向关系：每项验收都有负责工作；每项工作都服务已授权目标。没有归属的验收是漏项，没有目标的工作可能是多做。

### 1.1 必要时先形成有界的 Coding Task 契约

针对自然语言开发需求，借鉴历史 `spec_to_coding_task_skill.md` 的核心约束：**验收决定输出；输出决定输入；输入限制实现范围**。只补尚未明确的部分，不另起第二个任务管理系统：
- **输入契约**：项目已核实的技术栈、相关文件/调用方、必须保留的行为及约束；
- **输出契约**：本轮具体要改什么、明确不改什么、如何报告副作用与缺口；
- **验收契约**：可观察正常/异常行为、复用的现有检查、必须重新验证的风险和真实可执行入口。
检查规格来源、版本和用户授权，关键业务歧义交 Clarify；普通实现选择不必额外审批。不因已有一份模板就强制产出全量 YAML，也不从 AI 生成的实现反推测试预期。独立执行工作包仍统一使用 [共用委派包](../prompts/delegation.md)，Project 的 Task 不另行落盘。

## 2. 按可独立判断的行为划分

一个工作项应产生能单独接受或拒绝的结果。将必要初始化、配置和文档并入使用它的行为，不把“建目录”“写空接口”当作独立完成。

优先形成从输入到输出可检查的窄切片，而非先把所有层各写一遍才知道是否能工作。若变更必须跨多层共同成立，可以合成一个工作项，不能为了数量硬拆。

## 3. 用输入产出建立依赖

逐项回答：“它开始前，哪些产物必须已经存在并可用？”把这些作为前置边，而不是凭目录顺序排任务。

- A产生B要使用的接口/数据：先明确契约；契约仍不稳定则B等待或合并处理。
- 两项写相同文件/共享未定状态：串行或交同一执行者。
- 输入已齐且写入范围不重叠：才考虑并行。
- 出现循环依赖：补一个双方可遵守的接口约定，或把不可拆部分合并；不能让双方各猜一个版本。

顺序只由必要依赖决定。任务很多不意味着应全部并行，按层分类也不等于真实依赖。

## 4. 给执行者足够的决定

每项写明：
- 产物、对应验收条件、前置项；
- 读取/新建/修改的实际文件和所有者；
- 已决定的接口、字段、类型、错误语义与必须保留的行为；
- 具体动作、验证办法、预期现象和失败后的恢复位置。

先查仓库中真实构建/测试入口。没有运行环境就列可执行的后续验证及当前能做的检查，不能发明命令或预填PASS。

不要替执行者写完整程序，也不要只写“正确实现、覆盖边界”。计划应给出他无法从代码和规格自行知道的决定，普通实现细节沿用仓库模式。

## 5. 示范：增加可持久化的本地待办

假设已确认：现有CLI增加“添加、列出”，数据在重启后保留；沿用现有目录和文件格式，暂不做同步。相关入口和测试命令已查明。

- P1：确定存储读写接口及错误语义，完成“一条待办写入后可读取”的切片。使用实际接口名/路径，检查空存储和写入失败的既定行为。
- P2：将添加命令接入P1的稳定接口，验证新增后立即列出、重启后再列出。它依赖P1，不能独自发明另一种存储格式。
- P3：按验收检查空列表、已有数据和失败返回；测试材料可提前准备，依赖最终实现的行为验证需等P2完成。

若P1和P2改同一处入口，不派两个执行者同时改它。测试用例不能只验证内部函数存在；必须覆盖用户承诺的重启后结果。

## 6. 自检、输出与停止

按规格逐项检查覆盖；按依赖检查输入是否有产出；按接口检查名称/类型/错误是否一致；按文件检查是否冲突；按失败路径检查能否恢复或明确阻塞。

需要跨轮推进的工作项，在现有 Project 的 [Work Items 契约](../../project-management/schema/work-items.md) 下生成/更新 WI-ID、依赖、验收、下一动作；已存在的 WI 不重复创建。计划的长篇设计仍可放 work/ 作为引用，**权威工作项状态只保存在 work-items.md**。普通一次性任务无需强制拆解，也不建立独立 Turn Task 数据库。

目标、依赖和关键决定已足够执行时，按用户既定授权交给Execute或Orchestrate，不反复问“是否继续”。用户只要计划就交付计划；关键取舍尚未确定则指出具体问题，不用长计划掩盖它。

方法依据：S05的可验收工作、文件/接口/验证契约；验收反推、依赖检查和示范为本工作区适配。不采用自动commit或必须写满全部代码的做法。详见[来源](../references/sources.md)。未验证目标模型的执行效果。
