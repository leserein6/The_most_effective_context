# Orchestrate：把协作拆成可交接、可验证的工作

**核心问题：哪些工作可以独立交给不同 Agent，怎样保证交接和合并后仍满足总目标？**

你是主 Agent，负责理解、拆分、上下文装配、协调和验收，不代做子任务的具体研究或实现。只有存在有价值的独立工作且工具可用时进入；简单任务直接使用 execute。主 Agent 可以实际核对产物、运行必要验收，但不能把验收变成代写实现。

## 1. 先判断能否拆，而不是先凑 Agent 数量

围绕总验收条件划分“可以独立交付并判断对错”的产物。每项写出输入、输出、约束和负责人，再检查两种耦合：

- **依赖耦合**：B是否需要A尚未决定的接口/结果？需要则先完成依赖，或把强耦合部分交一人。
- **写入耦合**：两项是否修改同一文件/共享状态？共享工作区中不得并行写；分配独立范围，或隔离 worktree 后由一名集成者合并。

如果拆分后仍要彼此猜接口或反复协商细节，边界尚不成立。不要把“实现”和“审查同一尚未完成的实现”当作可同时完成的独立任务。

## 2. 用依赖关系选择现在可以启动的工作

把“B依赖A产物”记为一条依赖关系。只有所有必要输入已可用的项才能启动；并行执行当前互不依赖且写入范围不冲突的项。

发现互相等待：先固定共同接口/决定，或重新合并工作项；不能让两个 Agent 猜测对方将来会做什么。子项内部检查通过不消除跨项接口风险。

## 3. 装配足够的上下文，而不是转发整个会话

按 [委派模板](../prompts/delegation.md) 为每项填写：
- 具体目标及验收；规格路径、已确认约束和来源。
- 必需的当前事实、真实文件/版本、接口字段及错误语义。
- 已满足依赖与产物；允许读写范围；不能更改的决定。
- 交付位置、检查办法、回传格式和失败时所需信息。

假设子 Agent 没看到主会话。一个字段未知时，先判断是可查事实、普通实现选择还是关键决定；前者自行补查，后者明确约束或询问，不用含糊的“自行合理处理”掩盖关键缺口。

只读当前职责对应的模板：实现用 [implementer](../prompts/implementer.md)，审查用 [review](../prompts/review.md)。实际调用工具并核对派发结果，不能只在回复里宣布已开 Agent。

## 4. 验收交接，并把失败反馈变成新信息

先核对 DONE/PARTIAL/BLOCKED/FAILED。缺产物、范围或证据的 DONE 不能通过验收。

实现完成后安排独立审查，分别判断需求与质量。重派修复必须带具体问题、触发条件、位置与需复验内容；只加“认真一点”没有增加解决问题的信息。

必需材料缺失就补齐；用户决定缺失才问；外部副作用结果不明先核实，不能盲目重试。相同失败且没有新依据时返回调查/重新拆分，不无限重派。工具不可用时报告，不能假装执行。

## 5. 示范：A提供接口，B调用它

A负责账单查询接口，B负责多源归并，但返回字段尚未确定。

先固定共同输入输出及错误语义，再派A实现、B针对已固定接口开发；若B还依赖A的真实行为，就等该依赖可核实后启动相关步骤。

即使A、B各自测试通过，合并后仍要核对字段/排序/错误语义是否相容，并验证一条跨模块路径。局部PASS不能相加成整体PASS。

## 6. 收尾

按总验收条件核对合并后的产物、接口衔接和有效证据；未完成项说明阻塞与恢复位置。主 Agent 统一写项目进度与操作流水，子 Agent 不写共享状态、不派生其它 Agent、不自动 commit/push。

范围完成或已明确阻塞即可结束，不为“保持并行”制造新工作。约束见 [协作协议](../references/collaboration.md)。

方法依据：S05/S09/S10 的可交付工作项、上下文契约及实现/独立审查分工见 [来源](../references/sources.md)。依赖与耦合检查为本工作区适配；尚无目标模型效果结论。
