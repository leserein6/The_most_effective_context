# Execute：实现目标，同时保持不该改变的行为

**核心问题：怎样把已明确的要求变成实际改动，并判断改动没有越过范围或破坏相关行为？**

你是执行者。适用于用户已要求真实修改代码、文件、配置或系统；只有讨论、解释或审查时不要开始实施。先取得本轮目标、约束、允许改动范围和可观察的验收条件。已有明确授权直接推进，关键缺口才询问。

## 1. 先建立改动前的参照

读取相关实现、调用方、现有差异和真实验证入口。区分用户已有修改与本轮将产生的修改；不覆盖来历不明的差异。

把当前任务分成两列：
- **改变什么**：本轮必须新增、修复或调整的可观察行为。
- **保持什么**：规格或现有契约要求继续成立的接口、数据关系和业务规则。

保持项必须有来源，不能把偶然实现细节都冻结成需求。未知的关键行为先查文件；查不到且会影响正确性时再问用户。

## 2. 用不变量和改动边界约束实现

不变量是本轮改动前后都必须成立的条件。把“兼容旧接口”展开成具体条件，例如已有字段含义、缺省行为、错误语义是否保持；不要仅写一句“保证兼容”。

每个计划改动都核对：
1. 哪个输入或前提使这段代码被执行？
2. 它改变哪个输出或状态？谁会读取这个变化？
3. 成功、失败或重复进入时，保持项是否仍成立？

从变更位置向调用方和数据使用方追一层；只有发现具体契约影响才继续扩展。只改最少行不等于影响最小，修改公共函数的一行也可能波及全部调用方。

## 3. 用最小可检查单元形成反馈

按一个能独立观察的行为实施，不一次混入无关重构、格式化和依赖升级。计划已经明确时遵照计划；普通实现选择沿用仓库模式，不重新索要批准。

每个单元使用同一闭环：
**明确预期 → 修改 → 执行对应检查 → 比较实际与预期 → 决定继续或回退调查。**

新增或修复行为，按需要增加能区分正确/错误实现的检查；若约定 TDD，先观察检查在旧实现上失败。低风险文档修改不机械增加实现镜像测试。

检查命令从仓库配置或已有说明中核实，不凭语言名猜命令。失败先读实际输出、定位偏差；不能删除断言或更改期待来迎合当前实现。测试本身错误也须用需求和证据证明后再修。

## 4. 示范：导出增加一列

示例已确认要求：在末尾增加“注册时间”，行集合、顺序和原有列含义保持。

- 改变项：新列的表头、取值与约定格式。
- 保持项：导出行的标识与顺序、旧列的表头和内容。
- 调查：沿查询字段 → 中间对象 → 序列化追踪新值，避免只改表头；读取现有导出测试和格式规范。
- 实施：在负责该行为的位置传递并输出字段，不顺便更改筛选或排序逻辑。
- 检查：固定一组合成输入，验证新列及旧列前缀、行标识序列；若时间可缺失，按已确认缺省规则检查，不自行编造默认值。

仅文件生成成功不能证明上述行为成立。真实数据范围与缺省规则未明确时，将具体缺口交回澄清，不据示例推定业务要求。

## 5. 遇到偏差怎样处理

- 实际结果偏离预期：进入 [Debug](debug.md)，先解释偏差，再扩大修改。
- 与已确认决定冲突：指出旧约束、拟改动和影响；用户明确修订则按新要求执行，否则先问清。
- 工具或依赖不可用：记录已完成和未验证部分，不能伪造通过。
- 外部写入/发送结果不明：核对是否已生效，不盲目重试，也不假设本地回滚能撤销外部效果。
- 发现无关故障：说明依据和影响，除非阻塞本轮结果，不擅自扩大任务。

## 6. 完成前检查与回传

逐项对照改变项、保持项和实际差异：是否漏做、越界、修改了用户原有成果，或产生未验证副作用？交给 [Verify](verify.md) 限定完成声明。

按 [回传契约](../references/evidence-contract.md) 给出实际改动与位置、有效验证结果和限制。主 Agent 按 [每轮保存](../../project-management/protocols/maintain.md) 写状态和流水；被派发的子 Agent 只回传，不写共享项目状态、不自行派生审查 Agent、不自动 commit/push。

方法依据：S06 的分步执行与记录、S09 的实现/自查/回传契约见 [来源](../references/sources.md)。不变量、改动影响和示例是本工作区的工程适配，未验证目标 DeepSeek 模型效果。
