# 每轮执行流程

目标：让执行步骤明确、判断有分支、交接不靠记忆。只向用户显示结论和必要选择，不输出私有思维链，也不把本文件的表格每轮全部展示。

## 先备齐这六项

Project ID（归属不明先问）、本轮目标、已确认约束、所需资料位置、预期产物、验收办法。来源分为用户确认/文件事实/建议/未知，不能混写。缺少普通实现细节可自行选择并注明；缺少会改变目标或正确性的决定才询问。

## 固定顺序

| 步骤 | 做什么 | 通过条件 / 否则 |
|---|---|---|
| 1 锚定 | 查活跃 Index 与已有明确上下文 | 唯一匹配才继续；否则询问创建/接续 |
| 2 恢复 | resume，保留 token，读定义/当前状态/相关决策 | 缺失或冲突说明具体问题，不假装恢复 |
| 3 定任务 | 用一句话界定本轮结果，列出需满足的条件 | 信息不足进入 clarify；不要重问已确认项 |
| 4 选方法 | 按 Evidence 索引读取当前 README | 进入新阶段时补读，不预读全部文件 |
| 5 做工作 | 依对应步骤执行，收集产物和实际证据 | 测试/工具失败转 debug；授权关键冲突先问 |
| 6 验收 | 逐项将目标和实际证据对应 | 无证据标未验证，不用其它检查替代 |
| 7 保存 | 按 Project Maintain 写进度、操作流水、决策性质 | token 冲突重读比较合并，不能只换 token 重试 |
| 8 回复 | 结果、验证、未完成项；需要用户决定才提出问题 | 未保存/未验证准确说明，不能概括成全部完成 |

## 下一步选择规则

写 checkpoint 的 mode 只用脚本支持的七个名称：clarify/research/plan/execute/review/learn/orchestrate。design 记作 plan；debug 记作 execute；verify 与日志压缩属于当前主模式的检查/收尾，不另造 mode。若本轮只有独立验收，使用 review，并在 operations 写清实际检查。计划中的工作项编号不是持久 Task 实体。

- 资料中的事实缺失：先查文件/源码/工具，不把可查问题丢给用户。
- 用户意图或已确认约束有关键分歧：列旧值、拟改值和影响，等待决定。
- 只是实现方法有多个等价选择：遵循仓库已有模式，自行选择，不额外审批。
- 工具不支持：报告哪一步不能做及替代路径，不能模拟成功输出。
- 重复执行会造成额外扣款、发送或写入：先核对已发生效果，不盲目重试。

Project 的状态变化和公共规范纳入另有用户确认要求。完成本轮 Task 不自动把 Project 标为 completed。Task 不独立建长期数据库；计划与报告属于当前 Project 的产物。
