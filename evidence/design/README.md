# Design：决定要怎样实现目标

适用：架构、接口、数据模型、方案权衡；只是按既定方案执行时不重新设计。输入为已明确的目标/约束/验收条件，以及当前相关实现。

## 步骤

1. 查现有实现与规范，列需要维持的行为。把“用户要求”与“你的假设”分开。
2. 先写边界：本次输入/输出、谁负责、依赖谁、数据归属、哪些状态会变化。后画结构，最后才选组件。
3. 有实质取舍才比较方案；按相同维度比较正确性、复杂度、失败恢复、现有兼容性。只有一种合理实现时直接说明，不硬造三个方案。
4. 对选定方案走一遍正常路径和一个具体失败路径；明确调用顺序、错误返回、重试、并发或持久化影响。不相关项写不适用和原因。
5. 把关键规则变成可观察验收条件。交易/并发场景按需读工程风险清单；不拿通用“高可用”口号替代具体行为。
6. 检查是否冲突于已确认决定。关键方向变更问清；用户已授权的普通实现选择可自主完成。

## 输出

问题与目标；当前事实；边界/不变量；方案及取舍；选定接口与数据流；失败路径；验收条件；待决定项。

例：双主体账单分页，先规定排序键、游标、过滤和补齐规则，再讨论数据源调用；不能只写“并行查 A/B 后合并”。

完成条件：执行者能知道该保持什么行为、改哪里、怎样检查；有关键未知则转 clarify，有明确方案则转 plan/execute。写完设计不等于实现完成。
