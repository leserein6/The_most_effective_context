# 场景验收：测实际行为，不测模板关键词

参照来源 S11 的真实输入、基线对照、评价迭代方法，提供 [16 个用例](cases.json)。这些是可执行的人工/模型对话测试输入，尚未跑目标 DeepSeek 模型。它们不是应用单元测试，不应计入原有19项脚本测试数量。

## 怎样跑

1. 固定客户端、模型实际ID/版本、采样设置、仓库协议版本、工具权限与测试材料。记录可获得的配置，不猜API名称。使用隔离的临时项目/合成材料，不操作真实资金或外部发送。
2. 旧版和新版分别开新会话，在同样的 case context、request、资料和工具条件下执行。选择几项优先测试也可以，但必须写清覆盖范围。
3. 观察输出和工具轨迹：实际读了哪些文件、问了什么、写了什么、是否无授权操作、是否伪造完成。仅阅读协议或命中关键词不能算行为通过。
4. 对每项 must/must_not 按实际证据记录 PASS/FAIL/NOT_OBSERVED。未到达有关阶段写 NOT_OBSERVED，不把没触发错误算成功。
5. 有预算时每个版本重复若干次，记录结果波动、轮次、耗时/Token（能取到才记）。没有运行不填数值、不能报告提升百分比。
6. 优先修复关键失败：猜用户决定、忽略依赖并发覆盖、错误资金副作用、编造证据。格式好看不抵消这些错误。

## 记录格式

case_id；模型实际ID/客户端；协议commit；baseline/new；运行编号；输入材料版本；输出/工具轨迹位置；每条观察；关键失败；费用/耗时（可得才填）；结论与修订建议。

## 当前完成的检查

源码/方法来源已核对；协议的路由、依赖与冲突做静态检查，并安排独立审阅。独立审阅是对协议可执行性的检查，不是目标模型效果数据。后续真实执行结果应单独落盘，保留失败样例，不用改掉测试期待来隐藏问题。

## 入口读取轨迹补充

[routing-cases.json](routing-cases.json) 另列8个Task分类/读取场景。观察首条回复是否锚定Task、是否只读选中二级索引/当前方法、用户临时提问是否误取消任务。允许有效缓存和明确方法直达；不按“读文件次数越多越好”评分。这8个材料未在目标模型运行，不能报为8项行为测试通过。

开发型需求的[测试工程行为场景](testing.md)覆盖漏检、误拒与虚报通过，目标模型实测结果另记。
