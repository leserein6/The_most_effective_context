# 从行为承诺设计检查

先依据 [方法选择协议](selection.md) 抽取 Claim、错误机理、独立 oracle 与风险，再按 [方法目录](catalog.md) 和 [模型技术](models.md) 推导覆盖项及分母。不得从 AI 生成的实现直接复制预期结果。测试完成后还需 [充分性审查](adequacy.md)，不以用例数量当充分性证据。

1. 读变更前的规格、调用方和既有测试。把要求写成用户能观察的成功、失败及保持行为，注明来源或待决定事项。
2. 按后果和触发条件选择风险。字段边界选边界值；多条件选择决策表；事件顺序选择状态转换或故障注入；迁移选择契约、旧格式样本和必要的对照。参考实现只用于已确认应保留的行为。
3. 写出一个可能通过现有检查的错误实现。选择能区分它的输入、前置状态和观察位置。单元检查计算或分类，接口检查调用契约，存储集成检查持久效果，端到端检查用户入口。负载和恢复需匹配约定规模、环境与观察时间。
4. 固定合成数据、关键依赖、准备/清理办法，隔离并行运行。每个关键场景保存“需求 ID、依据、预期、风险、用例及层级”。计划中仍缺依据的条件进入 Project 未决事项。
5. 已覆盖的保持项直接引用。新增或修复的高影响行为，在可重现时用旧缺陷或代表性错误变体验证断言，再用另一种合法实现检查误拒。两次比较使用同一判据。

**书单例**。已有 A，合法新增 B、C 后重开应见 A、B、C。B 合法而 C 缺标题时，要求报错且重开后仅见原来的 A。逐行提交能给出正确错误提示，却会留下 B；因此要从新数据库连接读取完整书目。断言只约束这个结果，兼容预校验和事务两种实现。

规格已足够、重点风险都有可判别观察且环境明确，即可交给 [执行](execution.md)。形式化不了的用户体验、时间预算或平台条件单列，不能用其他检查代填通过。
