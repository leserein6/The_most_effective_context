# 审查、验收与持续回归

1. 从当前需求和调用方契约独立重列关键承诺，与测试计划交叉核对。检查是否遗漏失败后状态、约束了允许变动的实现细节，或把未知规格写成断言。后果高时请独立审查者重点核对判据与反例。
2. 对照候选版本、环境、夹具、实际命令和检查范围，阅读原始结果。核对失败或跳过的用例。故障来自产品、断言、环境还是偶发条件，写清实际依据；重跑保留首次记录。修改预期须能追溯到契约。
3. 按既有 [Verify](../methods/verify.md) 输出每项 PASS / FAIL / UNVERIFIED；关键承诺存在失败或未知时明确其交付影响。运行器汇总只是其中一份证据。审查和非自动化结论一并列入最终判断。
4. 将验收结论写入现有 checkpoint：operations 记执行和排查，evidence 用 kind/claim/source 引用具体结果；缺口放进 open_questions 与 next。只引用可在恢复后访问的路径或持久产物，临时目录中的证据先移入 work。恢复时先核对版本和契约变化，再复用相关结果。
5. 线上或验收后漏测，保存触发条件、可观察结果和最低可复现环境，加入对应业务回归集。若根因是 Agent 放过了未运行的检查，则维护者给 Harness 增加独立行为场景。跟踪漏检、误拒、虚报通过和运行成本，并保留样本分母。

审查完成标准是审查范围内的关键承诺都有明确判断、证据位置或待验证原因。Project 生命周期沿用原有用户确认规则。
