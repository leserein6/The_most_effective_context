# 测试充分性与证据审查：两个必须分开的问题

本页定义独立于测试运行器的**设计质量门禁**。test_gate.py 的 PASS 只意味着声明列入计划的 JUnit 测试在所执行环境中通过，不等于需求充分覆盖，更不等于系统无缺陷。

## Q0：我的测试证明了什么？

对每个 Claim 建立以下证据链：

需求/风险来源 → 可证伪的 Claim → Oracle → 测试模型和目标覆盖项 → 真实测试及执行环境 → 原始观察 → **有边界的结论**。

例如：“在 SQLite 的事务测试环境，已有一条 A；批次 B 有效、C 无标题；导入失败后新连接只看到 A”。
- 它支持：**这一输入与环境下**整批原子回退成立。
- 不支持：所有输入均原子、任意数据库隔离级别、断电不丢数据、任意并发安全。
- 如果测试只断言错误提示，不检查新连接存储结果，则不支持原子性结论。

声称“所有”“始终”“永不”需给出其形式化约束与证明前提，或缩小结论到已验证范围。观察到没有缺陷 ≠ 证明不存在缺陷。

## Q1：为什么这样测试是对的？

按以下顺序独立审查，**每一环都可能失效**：

| 审查项 | 检查方法 | 常见伪阳性 |
|---|---|---|
| 规格可信 | 需求来源、冲突、真实用户目标已确认 | 规格遗漏并发要求 |
| Oracle 正确 | 预期不来自被测实现或同一未经验证假设 | 实现与测试一起写错 |
| 方法适配 | 从失效机制推导 EP/BVA/DT/ST/MC/DC/CON 等 | 对事务只做 mock 单测 |
| 目标分母完整 | 枚举分区/边/组合/条件及排除依据 | 漏写高风险规则导致“100%” |
| 测试能杀错 | 代表性缺陷/变异体应失败；另一个合规实现通过 | 弱断言或绑死内部函数 |
| 实际运行可信 | 绑定候选快照、环境、夹具、真实原始日志 | 旧报告被拿来当新结果 |
| 变更后仍有效 | 影响分析 + 受影响回归重跑 | 修改了契约却沿用旧证据 |

**覆盖率必须报指标及分母**：
- 需求覆盖：有有效验证证据的相关需求项 / 当前受影响需求项（包含规格/ oracle 不确定项）；
- 等价类/边界：已测类或边界点 / 经审查的类或边界点；
- 决策表：已测有效规则 / 有效规则（不可达项单列）；
- 状态迁移：已测边 / 已定义可达边；必要时另列关键事件序列；
- 组合测试：已覆盖 t-way 元组 / 在约束下可行元组，必须记录 t、因子和约束；
- MC/DC：满足独立影响证据的原子条件 / 适用原子条件，排除耦合项需理由；
- 变异测试：被杀的非等价可执行变体 / 被评估的非等价可执行变体，超时/存活/疑似等价另列；
- 代码覆盖：语句/分支执行比例**仅反映执行**，不等于语义正确性。

缺失分母、未知可达性、等价变体未分类时，不得声称“充分覆盖”。风险允许有意识留白，但需记录残余风险与批准条件。

## 验收状态不应被压缩为单个 PASS

对关键 Claim 分开判定：
- **SPEC**：规格已确认/有冲突/未知；
- **DESIGN**：方法与覆盖义务已审查/有缺口/未验证；
- **EXECUTION**：按既有 test_gate.py 的 PASS/FAIL/UNVERIFIED；
- **ASSURANCE**：整体 PASS/FAIL/UNVERIFIED，附理由和适用范围。

只有 SPEC 已确认、DESIGN 已审查且无关键缺口、EXECUTION 有有效证据、关键非自动检查通过时，才可以对所列范围声明 ASSURANCE PASS。任何高后果未验证项不得被“多数通过”覆盖；可以明确交付被阻断或由有权人作出风险接受决定，**风险接受不是测试通过**。

“独立”指 oracle/模型/审查结论的来源与利益冲突被识别；不同 Agent 名字不等于真正独立。强制复核对象是规格与断言，不仅是代码。

## 交付时建议的最小摘要

- Claim / 来源和风险；
- 选用方法与理由，重要未选方法；
- 覆盖项与分母（含排除/未知）；
- 测试及运行环境和不可变候选标识；
- 设计审查结论、执行结论、残余风险、下一次回归触发条件。

即使运行器报 PASS，若测试方法选择未审查或存在遗漏的关键 Claim，最终只能报告 **DESIGN UNVERIFIED / ASSURANCE UNVERIFIED**。
