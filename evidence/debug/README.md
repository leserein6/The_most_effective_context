# Evidence: Debug（系统性调试）

**Use when**：出现 bug、异常行为、测试失败、性能退化、构建/集成错误，且需要诊断或修复。  
**Don't use when**：单纯新增功能，没有异常事实。

## 先调查、后修复

1. **捕获症状**：完整错误、发生环境、重现步骤、输入输出和最近变化。复现不了时先补观察信息，不直接猜根因。
2. **缩小故障范围**：沿数据/调用路径检查分层边界，识别哪里开始偏离预期；利用日志、差异、最小复现实验。
3. **提出可证伪假设**：每次只测试最可能的一个原因；用可观察结果排除或支持，避免同时改多个变量。
4. **定位机制后修复**：说明根因与证据；再进入 [Execute](../execute/README.md) 做最小修复。
5. **验证原始症状与回归**：修复后调用 [Verify](../verify/README.md)，确认原故障路径及相关测试；改了代码但没有复验不能声称修复。

## 失败门槛

- 不知道根因 → 标记尚未定位，不连续试错式提交补丁。
- 复现条件不可靠 → 收集额外诊断，不编造“稳定复现”。
- 测试失败 → 保留失败状态，别用另一项测试通过来覆盖。

**参考方法**：Superpowers `systematic-debugging` 的四阶段根因调查、假设、修复和验证；本协议采用最小版本、不依赖特定调试框架。
