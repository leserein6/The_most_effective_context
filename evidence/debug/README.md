# Debug：用可区分的证据定位偏差原因

**核心问题：观察到的错误由什么机制产生，哪项检查能够区分不同解释，怎样证明修复针对了原问题？**

适用于失败测试、异常结果、性能退化或环境故障。你的任务是减少原因的不确定性；不能把“代码看着可疑”当作定位，也不能用连续补丁代替调查。

## 1. 固定症状与比较基准

记录同一问题的输入、预期、实际、环境/版本和复现入口。预期来自需求、契约或可靠参照；若预期本身有争议，先澄清。

区分稳定复现与偶发发生。无法复现时收集必要观测，不立即改业务逻辑。保留用户已有改动，避免为“恢复干净环境”删除未知成果。

## 2. 找第一处偏离，而不是只盯最终报错

沿输入 → 调用 → 中间数据/状态 → 输出检查，比较各边界的预期与实际。找到最后一个符合预期的位置，以及第一个不符合的位置，再调查二者之间的机制。

用正常与异常案例对比时，先列两者真正不同的输入、配置、版本或执行顺序。差异只是线索；“最近改过”不自动证明它是原因。

## 3. 把猜测变成可证伪假设

每个主要解释使用三个字段：
**假设 H → 若成立应观察到什么 → 什么观察会与它冲突。**

优先选择不同假设会产生不同结果的检查。只会重复确认“系统确实失败”的日志，没有区分原因的能力。

一次检查尽量只改变一个相关条件，固定其余输入/环境；若做不到，列明同时变化的因素，不能把结果唯一归因于其中一个。观测或调试代码也可能改变并发/时序，要记录这种限制。

结果与假设相容只表示暂未排除，不等于确认。其他解释仍成立时，继续找区分证据；不要仅因排除了一个就宣布另一个成立。

## 4. 示范：分页过滤后经常不足一页

示例要求：只要仍有符合条件的数据，就补足目标页长。

已观察：请求10条，返回3条。至少有两种解释：
- H1：底层只取一次固定批次，过滤后没有继续补齐。
- H2：目标范围确实只剩3条符合条件的数据。

反复运行同一接口看到3条，不能区分 H1/H2。

选择一组合成数据，确保当前游标之后存在足够的符合项，并固定排序、过滤条件与游标；观察实际拉取批次和过滤结果。同时检查有无继续拉取的控制流。

若首批10条过滤剩3条、后面还有符合项，且实现未再读取，可把该症状联系到缺少补齐路径。若始终只有3条符合项，返回3条未必是故障。若同时改了游标和数据集才出现变化，不能独立证明哪个改动有效。

## 5. 修复必须与原因和原症状闭合

能说明“输入条件 → 具体机制 → 偏差结果”后，进入 [Execute](../execute/README.md) 做针对性修改，不顺便重构无关模块。

保留能触发原问题的回归检查；修复后在相同条件下检查原症状，并验证受影响的保持项。新案例通过不能代替原故障路径复验。

- 假设被否定：记录排除依据，回到边界调查，不继续加同类补丁。
- 连续两次修复未改变症状且没有新证据：停止新增补丁，重审复现/根因。两次是本地防循环约定，不是普遍科学阈值。
- 只能定位某段链路：报告已知区间与下一项观察，不编造完整根因。
- 环境缺失或外部结果未知：记录阻塞/已发生效果；尤其不能把调用超时直接解释为下游未执行后重发。

## 6. 输出与停止

回传症状和复现范围、关键观察、假设与判别结果、已定位机制或未知区间、修改及回归证据。区分事实与推断，不输出私有思维链。

根因机制得到足够依据且原症状复验通过，才向 [Verify](../verify/README.md) 提交“已修复”声明。否则明确未定位、部分定位或未验证，以及缺少的具体观测。

方法依据：S07 的复现、边界调查、假设检验和回归见 [来源](../SOURCES.md)。控制变量、判别实验、示例与防循环规则为本工作区适配，未验证目标 DeepSeek 模型效果。
