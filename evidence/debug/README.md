# Debug：先定位偏差，再修复

触发：失败测试、错误结果、异常、性能退化或环境故障。先区分观测事实和猜测；“我认为是缓存”不是定位结果。

## 顺序与通过条件

1. **复现**：记录完整错误、输入、预期/实际、版本和执行入口；用最小步骤尝试复现。无法复现先补日志/环境信息，不先改业务逻辑。
2. **定位边界**：从请求入口沿调用/数据路径追踪，比较哪个位置开始不符合预期；检查有关配置和最近差异。
3. **形成假设**：写“如果原因是 X，则观察 Y 应出现 Z”。每次用一个有判别力的检查确认或排除，记录实际结果。
4. **解释机制**：将错误与具体文件/分支/条件联系起来；能解释为何该输入触发错误，才开始修复。
5. **最小修复**：切 execute，修原因；若能构造有意义的回归检查，先确认它覆盖原始失败。
6. **复验**：原始触发路径重新检查，再覆盖受影响行为；到 verify 决定能声明什么。

## 不同结果怎么走

| 观测 | 下一步 |
|---|---|
| 假设被否定 | 记录排除结果，回到边界调查，不继续叠补丁 |
| 连续两次修复未改变症状 | 停止新增补丁，重新核对根因/复现；本阈值是本地防止无效循环的规则 |
| 环境依赖缺失 | 作为阻塞处理，不宣称业务 bug 已修复 |
| 仅能确认部分链路 | 报告已定位区间与下一项观察，不编造完整根因 |

## 输出

症状与复现；已知事实；假设→检查→实际结果；根因定位或未定位范围；修改与回归证据。

例：提现返回超时不能直接推出银行失败；先核实请求到达/查询结果/本地状态，再决定补偿，不能直接重发或解冻。
