# 从一个点展开工程全景

先说明对象、用途和边界。区分通用能力图与具体系统的现状图。前者记录可能承担的职责、机制及适用条件，后者只记录当前版本可定位的行为。若局部问题已有明确边界，沿当前分支处理即可。

1. **选种子。** 已有适用的图就直接采用，标注来源与范围。微服务优先用[九个能力域](maps/microservice.md)。没有图，从一个能定位的真实入口开始，例如一次查询、一个 API、一条发布配置或一份规范章节。写下当前为什么选它。
2. **沿可核实的关系追一层。** 问谁调用它、它依赖谁、它持有什么资源、谁负责释放、失败结果交给谁。每次只沿能说清的关系扩展，记录起点、关系、发现和出处。新术语或模型记忆可以提出检索问题；查证后再决定是否收录。
3. **换入口找盲区。** 第一个种子决定了能看到什么。只有成功读请求时，再从写入、退出、部署或故障记录中选一个能暴露遗漏的入口。画通用图时用独立的规范或另一种实现检验适用范围；在单一实现中观察到的特性保留其实现限定。技术生态单独映射“能力 → 标准库、框架或平台 → 提供条件”。
4. **按职责归类。** 将证据支持的具体机制归入上层分支。给树上每项保留一个主要归属，跨域关系用引用表达。区分用户提供的分类、已核实的机制、当前项目的证据和待查假设。既有图的覆盖和命名是可复用的起点，推断某项目已经部署某能力需另取证。
5. **停止并交付。** 优先展开会改变本次决定的分支。记录独立入口补出了什么，尚有哪些分支验证不了，为什么当前证据已足够作决定；关键证据不足时明确交付局部图。项目特有实例或调查结论随 Project 记录，跨项目复用候选沿现有知识积累协议处理。

## 小例子 · 从一次 Go 多行查询出发

| 种子与关系 | 可纳入的分支 | 证据与范围 |
|---|---|---|
| QueryContext 返回 Rows，调用者遍历并 Scan | 结果遍历、字段映射 | [Go 查询示例](https://go.dev/doc/database/querying)，适用于 database/sql 路径 |
| Rows 需要结束遍历、关闭并检查后续错误 | 资源生命周期、错误处理 | 同一示例中的 Close 和 Err |
| 查询接收者 sql.DB 管理连接池 | 连接复用、连接池约束 | [Go 连接管理](https://go.dev/doc/database/manage-connections) |
| 换成一次涉及两项写入的事务，从 BeginTx 追到 Commit 或 Rollback | 事务边界与失败处理 | [Go 事务指南](https://go.dev/doc/database/execute-transactions) |

以上证据支持一张局部图。要评估本项目是否需要读写分离，可继续找项目的数据源配置与路由实现在何处生效。仅凭这段查询代码，读写分离仍是待查问题。

滚雪球的检索思路借鉴 [Wohlin 的文献追溯方法](https://doi.org/10.1145/2601248.2601268)。用调用、配置、所有权和生命周期关系扩展工程对象，是本 Harness 对这一思路的应用。
