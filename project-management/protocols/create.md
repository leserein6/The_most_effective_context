# Project Create · 创建协议

**激活条件**：用户希望将某个长期工作正式建立为可持久化 Project，而非只是询问或讨论一个想法。

## 创建门槛

- 项目要解决的问题、预期结果已足以区分该项目和其他项目。
- 不存在会改变创建授权、范围或重要风险的未澄清问题。
- 用户看过**具体草案**并对这份草案表达明确确认。

非关键字段可以待定；不以完整填满表单作为创建前提。

## 执行步骤

1. **判别意图**：先确认用户是否真的要求长期 Project；单轮 Task 不自动创建。
2. **收集已知信息**：依据用户原话提取问题、预期结果、边界、交付物、约束；进入字段生成前读取 [Definition 契约](../schema/definition.md)。
3. **按需澄清**：如果关键信息缺失或相互矛盾，调用 [Grill-me](../../harness/protocols/clarify.md)，优先问一个影响最大的点；清楚就不问。
4. **形成草案（尚不写入正式实例）**：展示项目名、问题、预期结果、范围、预期交付物、关键约束、待定项，以及建议的第一个行动。仅当提取方式不清晰时读取 [Few-shot](../examples/intent.md)。
5. **确认门槛**：明确请求「按以上草案创建吗？可以修改哪些点？」。初始“帮我创建项目”是任务授权，不等于对 AI 自拟草案的认可；用户修改后重新呈现受影响内容。
6. **用户确认后落盘**：读取 [Schema 索引](../schema/project.md) 和 [模板](../templates/project.yaml)；核查目标 `projects/<id>/project.yaml` 不存在，写入实例，不用空白/虚构值冒充用户决定。
7. **验证**：重新读取创建的文件，核查关键字段与确认草案一致、路径存在、无 ID 冲突，然后反馈真实路径、已确认内容和下一步。

## 不能做的事

- 未得到对具体草案的确认就建立正式 Project。
- 因用户说“可以先做”而擅自扩大项目范围。
- 把自己提出的功能列表、技术选型或验收项说成用户确认过。
- 因暂时不知道非关键技术细节，强制无穷追问。

**异常**：遇到同名/同 ID、写入失败、权限不足或确认内容模糊时先报告冲突；不得覆盖现有项目或假装成功。
