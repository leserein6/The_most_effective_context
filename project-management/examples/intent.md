# Few-shot · Intent 提取、澄清、变更

**仅在需要对照提取/变更判断时加载。** 示例中的话不是当前用户的事实，也不代表创建/更新授权。

## A：很模糊，不应直接创建

**用户**：「我想做一个 AI 知识整理 App。」

**错误**：直接决定要移动端、向量数据库、云端同步，然后写入 Project。

**正确判断**：还不知道主要要解决哪个知识整理问题；影响产品定位，需要进入 Grill-me。

**合适回复**：「我理解你想做一个 AI 知识整理工具。你最希望它先改善哪件具体事情：收集资料、检索已有笔记，还是把材料整理成可复用知识？」（让用户自由补充）。

## B：信息足够，先给草案再确认

**用户**：「想让 AI 跨 Session 继续开发；首版只支持创建、更新、恢复，暂不做多 Agent。建一个 Project。」

**正确草案片段**：

```yaml
intent:
  problem: "新 Session 缺少可复用的项目状态，需要重复解释"
  desired_outcome: "跨 Session 可靠创建、维护、恢复长期项目"
  success_signals: null  # 先提出候选验收方式，尚未确认
scope:
  in: ["创建", "维护", "恢复"]
  out: ["多 Agent 编排"]
```

**正确动作**：展示草案、指出验收标准尚待确定，请用户确认后才正式写入 `projects/`。

## C：功能任务不构成意图变化

**已有项目**：「可靠恢复长期项目的工作状态。」

**用户**：「在恢复流程上增加缓存。」

**错误**：把 `intent.desired_outcome` 改成「高性能缓存系统」。

**正确**：按功能/设计任务处理；必要时更新范围和进度，不动核心意图。

## D：重大范围变化应先确认

**已有范围**：仅支持一个 CLI。

**用户**：「以后要通用，能支持不同的 Agent。」

**正确判断**：可能是方向扩张，需展示拟修改 `scope`、`intent` 及交付影响。用户确认后更新，不悄悄覆盖过去决定。

## E：用户纠正推断

**AI 草案**：「必须云端部署。」

**用户**：「不对，我只要本地工具。」

**正确**：删除未获确认的云端要求，记录本地约束并修订草案；旧推断不能继续作为既有事实。
