# Project Schema & Field Maintenance Contract (V0)

**用途**：定义实例中各字段的语义，以及 AI 如何从用户话语中提取、判断是否更新、避免擅自补全。创建或维护时只读取涉及的字段部分；示例另见 [Few-shot](../examples/intent.md)。

实例的结构模板：[project.yaml](../templates/project.yaml)。

| 字段 | 定义（Definition） | 提取（Extraction） | 更新条件（Update）与禁止事项（Constraints） |
| --- | --- | --- | --- |
| `id` | 稳定项目标识 | 从经确认的名称生成唯一、可读 ID | 创建后不随标题变更而更改；避免覆盖已有 ID |
| `name` | 用户可识别的名称 | 优先采用用户用词；否则提出简短名称让用户确认 | 用户明确要求改名时变更 |
| `intent.problem` | 该项目要解决的核心问题 | 提炼用户当前痛点，保留含义 | 新证据可形成修订提议；不得自造痛点 |
| `intent.desired_outcome` | 期望最终达成的状态或成果 | 从用户预期结果中总结，不写实现步骤代替结果 | 重大方向变化先确认，不因普通子任务自动改变 |
| `intent.success_signals` | 判断是否达成意图的可观察标准 | 使用用户给出的验收标准，缺失时建议而非冒充确认 | 重大验收标准变化先确认；无依据留空或标待定 |
| `scope.in` / `scope.out` | 项目边界 | 汇总确定包含、排除的内容 | 增减关键范围先确认，不能把建议自动写入 |
| `deliverables` | 可交付成果 | 汇总用户明确需要的产物 | 经用户认可或已实现的新成果可更新，区分计划与实际 |
| `constraints` | 成本、技术、时间、行为限制 | 忠实提取明确约束与不可违反的限制 | 只在得到新授权/核实变化后调整，不得默默丢弃 |
| `state.phase` | 项目生命周期状态 | 依据已确认事实标为 draft/active/paused/completed/archived | 阶段转换以实际状态和用户指令为依据 |
| `state.summary` | 可靠、简短的当前进度 | 从实际产物与验证结果概括 | 执行产生可确认进展后更新；不写推测成事实 |
| `state.next_action` | 目前最合理的接续动作 | 从剩余工作与用户优先级提炼 | 随进度更新，可标明「建议」与「已确认」 |
| `state.blockers` | 当前阻塞因素 | 根据真实失败、缺失输入与依赖提炼 | 阻塞解决时清除，保留相关证据引用 |
| `references` | 历史、决策、证据的相对路径 | 指向真实存在的文件 | 文件不存在时不得伪装引用有效 |

## 状态与数据分层

- **Project 实例**只保存经确认的稳定描述、简短状态、资源引用。
- **字段契约**是所有实例共享的 AI 操作规范，不复制到每份项目文件。
- **Few-shot**按需读取，不把示例数据当作用户项目事实。
- **历史**保存在另外的文档（如 `decisions.md` / `journal.md`），V0 不要求每轮写完整聊天记录。

## 修改原则

1. 区分用户明确提出的事实/决定、AI 建议、待核实假设。
2. 新的信息只更新受影响字段；与原有事实冲突时先澄清或明确处理依据。
3. 重大变更须展示差异并确认；小幅状态刷新也应以可检查结果为依据。
4. 更新后重新读取或核验目标文件，避免只凭工具调用成功假定数据正确。
