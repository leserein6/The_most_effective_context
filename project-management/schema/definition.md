# Project Definition · 核心字段维护契约

**适用**：创建 Project，或变更其身份、长期意图、边界、预期成果和硬约束。不要为普通进度更新加载此文件。

每个字段遵循：**定义 → 从用户输入提取 → 什么时候更新 → 不允许怎样更新**。

| 字段 | Definition（是什么） | Extraction（怎么总结） | Update（何时更新）与 Constraints（禁忌） |
| --- | --- | --- | --- |
| `schema_version` | 实例结构版本 | 按当前模板确定，V0 为 `"0.1"` | 仅正式迁移时修改；不能把内容变化当结构迁移 |
| `id` | 不随名称更改的稳定标识 | 根据确认后的项目名建议 slug，检查与既有实例不冲突 | 原则上不可变；不能覆盖其他 Project |
| `name` | 用户用来识别项目的简短标题 | 优先用户原话，必要时给出候选待确认 | 用户明确改名后可修改；不必连带改 ID |
| `intent.problem` | 要解决的核心问题或缺口 | 从痛点/现状中概括**为什么需要此项目** | 改变核心问题属于重大变更；不能根据解决方案倒推出虚构痛点 |
| `intent.desired_outcome` | 期望达到的外部结果/状态 | 从用户希望实现的能力、价值总结**做到什么算达成** | 重大方向变更先确认；不等同具体技术选型 |
| `intent.success_signals` | 可观察的验收信号 | 优先用户明确标准，缺失时给出候选建议并标未确认 | 更改关键验收口径先确认；不把 AI 建议默认为已采纳 |
| `scope.in` / `scope.out` | 当前明确包含/排除的范围 | 仅汇总用户明确界定的能力及不做项 | 改变承诺的关键范围先确认；没有提及“不做”不等于排除 |
| `deliverables` | 计划交付的具体成果形式 | 从用户预期可交付物提取（代码、文档、工具等） | 区分计划成果和已交付成果；已交付信息进入 `state.verified_outputs` |
| `constraints` | 预算、时间、平台、技术、权限等硬限制 | 精确保留数字、平台和否定要求 | 不得自行放宽或删除约束；冲突先澄清 |

## 提取顺序与质量门槛

1. 先提取用户**明确陈述**的内容，再独立标明自己的推断/建议；后者不得冒充确认事实。
2. 首要确认 `intent.problem`（为什么做）与 `intent.desired_outcome`（要达到什么），至少能描述项目方向。具体技术栈不是必填项。
3. 对未明确的可选项记录待定，**不要用为填满结构而编出的字符串**。重要待定项影响是否可创建，由 [Create](../protocols/create.md) 决定。
4. 用户纠正之前的提取时，以最新明确表述为准；如产生重大分歧，展示旧值与拟改值让用户确认。
