# 接到新任务 SOP

## 目标
将非结构化交办变成「明确交付契约 + 可执行步骤 + 可验证完成标准」，而不是立即开始写代码或自动建 Project。

## 事实来源
先检查已锚定 Project 的 definition/state/acceptance 和现有 Work Item（如存在），再看用户提供的聊天记录、需求文档、工单。缺少归属先向用户确认；不得虚构 Project/WI、干系人或时间。将「需求方明确要求」「用户理解」「AI 推测」分开。

## 执行流程
1. **确认六件事**：做什么、给谁/谁验收、何时交付、交付格式、验收条件、范围/依赖。已知不重问；仅就阻断执行的未知项追问，其他项标「待确认」。
2. **写交付契约**：一句话目标 + 范围内/外 + 具体产物 + 可观察验收信号。针对软件需求补充环境、接口、边界与回归要求；未经明确确认不能推定上线等于验收。
3. **拆解**：按依赖与风险排序；每项明确产出、完成标准、前置依赖、已知负责人和截止时间。优先解除阻塞关键路径的事项；未知工期只给估算及依据，不编造硬截止。
4. **制定第一步**：给一个立即可执行的动作，说明完成后检查什么。
5. **闭环**：需要对方回答的，提供简短确认消息草稿；用户明确要求记录时，通过 Harness 既有 WI/Project 协议写入，不能新建重复待办数据库。

## 默认输出
- 任务契约：目标｜接收方｜交付物｜截止｜验收。
- 待确认：问题｜为什么影响交付｜该问谁。
- 执行步骤：工作项｜依赖｜顺序｜验收依据。
- 第一动作：现在做什么。

## 停止条件
关键验收/权限未明确时不擅自承诺工期或实施不可逆变更；用户只要确认消息就仅生成消息。用户没有授权时不发送消息、修改外部工单或创建项目。
